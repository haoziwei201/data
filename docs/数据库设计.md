================================================================
基于 MongoDB 的问卷系统 —— 数据库设计思路（第一阶段）
定位：可扩展、可维护，并为第二阶段需求变更预留演进空间
================================================================

〇、设计总原则
----------------------------------------------------------------
1. 面向"访问模式"设计，而不是把关系型 ER 图原样搬进 MongoDB。
   先问"系统怎么读、怎么写数据"，再决定文档边界。
2. 一个文档 ≈ 一次业务读取的完整单位（聚合根思想）：
   渲染一份问卷 = 1 个 survey 文档 + N 个 question 文档；
   提交一次问卷 = 插入 1 个 response 文档。不需要多表连接。
3. 一切会变的业务规则（题型、校验规则、跳转规则）全部"数据化"，
   存在文档字段里；代码只负责"解释执行"这些数据，不写死任何
   具体题目的逻辑。这是"逻辑不写死在代码"的落地方式。
4. 为第二阶段预留演进路径：软删除代替硬删除、type/status 用
   字符串而非魔法数字、文档带 schema_version、留 settings
   扩展位。改需求时"加字段"而不是"改结构"。
5. 克制冗余：只保留有明确用途、可承受维护成本的冗余；杜绝
   无界数组（不把答卷嵌进问卷文档）。

一、总体架构：4 个核心集合 + 1 个可选缓存集合
----------------------------------------------------------------
集合              职责                          对应业务
users             用户账号                      注册 / 登录
surveys           问卷元信息与生命周期          创建 / 发布 / 关闭 / 列表
questions         题目（选项、校验、跳转规则）  出题 / 填写时渲染与判卷
responses         答卷（一份答卷一个文档）      提交 / 统计
survey_stats      统计结果缓存（可选，按需启用） 高频查看统计

说明：题目不嵌入 surveys、答卷不嵌入 surveys，理由见"三、D1/D2"。
集合名与字段名统一用英文小驼峰，避免后续编码/驱动兼容问题。

二、集合详细设计
----------------------------------------------------------------
2.1 users —— 用户
{
  "_id": ObjectId,
  "username": "zhangsan",              // 唯一，登录名
  "passwordHash": "$2b$10$...",        // 只存哈希，绝不存明文
  "createdAt": ISODate("2026-10-17"),
  "status": "active",                  // 预留：active/disabled
  "profile": { }                       // 预留扩展位（昵称、邮箱等）
}

2.2 surveys —— 问卷（只放"清单页需要的信息"，不放题目和答卷）
{
  "_id": ObjectId,
  "ownerId": ObjectId,                 // 创建者，指向 users._id
  "title": "大学生生活习惯调查",
  "description": "请如实填写，感谢配合",
  "slug": "aB3xK9",                    // 对外 URL 标识：/survey/aB3xK9
  "status": "published",               // draft / published / closed
  "allowAnonymous": true,              // 是否允许匿名填写
  "allowMultipleSubmissions": false,   // 同一人是否可多次填写
  "deadline": ISODate("2026-11-01T23:59:59"),
  "settings": { },                     // 扩展位：第二阶段新开关都放这里
  "schemaVersion": 1,
  "createdAt": ISODate,
  "updatedAt": ISODate
}

要点：
- slug 独立于 _id：对外暴露的短链接不泄露内部 ID；_id 变更或
  换存储都不影响已分发的 URL；slug 建唯一索引。
- 截止时间到期是否算"关闭"：读取时用 status + deadline 联合判断
  （deadline 已过视为不可填），不必依赖定时任务改状态，避免状态
  与时间不一致；手动关闭才把 status 置为 closed。

2.3 questions —— 题目（本设计的核心）
公共结构 + 按 type 区分的 config，即"判别联合"模式：
{
  "_id": ObjectId,
  "surveyId": ObjectId,
  "order": 3,                          // 在问卷中的顺序，从 1 开始
  "type": "single_choice",             // 见下方题型清单
  "title": "你的性别",
  "required": true,
  "config": { ... },                   // 随 type 变化的配置（校验规则）
  "jumpRules": [ ... ],                // 跳转规则（见 2.3.4）
  "deleted": false,                    // 软删除标记
  "schemaVersion": 1,
  "createdAt": ISODate,
  "updatedAt": ISODate
}

2.3.1 题型与 config（校验规则全部是数据）
a) 单选题  type: "single_choice"
   "config": { }
   "options": [
     { "key": "opt_male", "text": "男" },
     { "key": "opt_female", "text": "女" },
     { "key": "opt_other", "text": "其他" }
   ]
   （options 与 config 平级，choice 类题型专有字段）

b) 多选题  type: "multi_choice"
   "options": [ { "key": "opt_apple", "text": "苹果" }, ... ]
   "config": { "minSelect": 2, "maxSelect": 3 }   // 缺省 = 不限
   // "必须选 2 个" = minSelect = maxSelect = 2

c) 文本填空  type: "text"
   "config": { "minLength": 5, "maxLength": 200 } // 缺省 = 不限

d) 数字填空  type: "number"
   "config": { "min": 0, "max": 120, "integer": true }
   // 例：年龄 min=0 max=120 integer=true
   // 例：手机号 integer=true（11 位数字仍在数值安全范围内；
   //     若担心更长数字，可存字符串并用正则校验，type 不变）

要点：
- 所有校验参数都是普通字段：需求变更（如新增"最多选 N 项"）只改
  config 内容或加同类型字段，数据库结构不动。
- 新增题型 = 新增一个 type 字符串值 + 一段校验代码（见"七"），
  历史题目完全不受影响。

2.3.2 选项用 key（稳定机器标识），不用选项文本
- 答卷、跳转规则里存的都应是 options[].key，绝不存"男"这种文本。
- 修改选项文字（如"男"→"男性"）不影响已有答卷与统计含义；
- 删除选项后 key 永不复用，新增选项一律生成新 key，
  历史数据因此永远不会被错误映射。

2.3.3 跳转规则 jumpRules（统一条件模型，数据驱动）
规则语义：填完本题后按数组顺序逐条匹配，命中第一条即执行其
goto；全部不命中则默认进入 order + 1 的下一题。
[
  { "match": { "kind": "option_any",
               "optionKeys": ["opt_a"] },
    "goto": "<question_id_5>" },

  { "match": { "kind": "option_all",          // 多选：同时选中才跳
               "optionKeys": ["opt_a","opt_b"] },
    "goto": "<question_id_3>" },

  { "match": { "kind": "number",              // 数字填空：比较
               "op": "lte", "value": 18 },
    "goto": "<question_id_4>" },

  { "match": { "kind": "always" },            // 兜底（可省略）
    "goto": "end" }                           // "end" = 提前结束问卷
]

要点：
- goto 存目标题目的 _id（稳定），界面展示时换算成"第 N 题"；
  题目增删、重排后跳转目标依然正确。若存 order，重排即全错。
- kind 目前覆盖需求的三种跳转依据（单选/多选/数字）；将来要
  "组合条件（且/或）"，只需让 match 支持 conditions 数组 +
  combine 字段，旧的单条件视为只有一个元素的组合，天然向后兼容。
- 数字 op 支持：eq / ne / gt / gte / lt / lte / between（配
  min、max）。

2.4 responses —— 答卷（一次提交 = 一个文档）
{
  "_id": ObjectId,
  "surveyId": ObjectId,
  "respondent": {
    "userId": ObjectId,        // 登录填写者；匿名时为 null
    "anonymous": false
  },
  "submittedAt": ISODate,
  "answers": [
    { "questionId": ObjectId, "value": "opt_female" },      // 单选
    { "questionId": ObjectId, "value": ["opt_apple",
                                        "opt_banana"] },    // 多选
    { "questionId": ObjectId, "value": "经常熬夜" },        // 文本
    { "questionId": ObjectId, "value": 21 }                 // 数字
  ],
  "meta": { "ip": "...", "userAgent": "..." }   // 可选：审计/防刷
}

要点：
- value 的形态由对应题目的 type 决定：单选=一个 key 字符串，
  多选=key 数组，文本=字符串，数字=数值。读取方根据题目定义解释。
- answers 内不冗余题目文本、不冗余 order：题目信息以 questions
  为唯一事实来源，统计展示时在应用层做一次内存合并（题目定义
  一次性查出，代价极低），避免冗余数据随题目编辑而失真。
- 一份答卷通常几十上百题，文档远小于 16MB 上限，嵌入安全。

2.5 survey_stats —— 统计缓存（可选，先不建）
{
  "surveyId": ObjectId,
  "computedAt": ISODate,
  "data": { ...聚合结果... }
}
初期直接用聚合管道实时计算（见"六"），准确且零维护成本；
仅当数据量大到统计变慢时再启用此缓存：读取时若 computedAt
晚于最新 submittedAt 则直接用缓存，否则重算并覆盖。
这是"谨慎使用冗余"的示范：冗余必须换来明确收益，且能自愈。

三、关键设计决策与理由
----------------------------------------------------------------
D1 为什么 questions 独立成集合，而不是嵌入 surveys 文档？
  - 题目数量开放（无界），嵌入式文档会随题目增多不断膨胀；
  - 编辑题目只写一个小文档，不触碰 surveys，减少并发冲突面；
  - 单题统计、按题查询（跳转目标解析）更直接；
  - surveys 保持轻量，正好承载"我的问卷列表"这类高频查询。
  代价是渲染问卷要 2 次查询（survey + questions），完全可接受。

D2 为什么 answers 嵌入 response，而不是每题一个文档？
  - 答卷的写入单位、读取单位都是"整份提交"，从不单独读某题
    的某次回答；拆开只会让一次提交变成 N 次写入，且失去原子性。
  - 反方向同理：答卷绝不能嵌入 surveys —— 无界数组 + 并发热点
    + 16MB 上限，三条死罪。

D3 为什么选项/答案存 key 不存文本？
  见 2.3.2。文本是展示层的东西，会改；key 是身份，不改。
  这一条同时保住了统计正确性和跳转规则稳定性。

D4 校验为什么做成 config 数据而不是代码里的 if-else？
  每道题的限制都不同，写进代码等于每题一段程序，无法维护。
  数据化后：新增限制种类 = 新增一种字段解释器；改限制 = 改数据。

D5 跳转为什么做成统一 match 模型？
  三种跳转依据（单选/多选/数字）抽象成同构的"条件 + 动作"，
  解释器只有一个；扩展条件类型不再碰存储结构（见 2.3.3）。

D6 统计为什么"实时聚合优先"？
  维护冗余计数（如 survey.responseCount 每次 $inc）会引入
  热点写入与数据漂移风险；课程规模下聚合毫秒级完成，先简单
  后优化，缓存作为预留手段（2.5）。

D7 并发与重复提交怎么处理？
  - 多人同时填写：各写各的 response 文档，互不读写对方数据，
    天然无冲突；这也是不把计数器挂在 surveys 上随提交自增的
    原因之一（避免对同一文档的高频争用）。
  - 防同一人重复提交（allowMultipleSubmissions=false 时）：
    提交前查一次（surveyId + respondent.userId）+ 插入；课程
    规模下足够。若要严格防并发重复，可用确定性 _id 方案：
    此类问卷的答卷 _id 固定为 "{surveyId}:{userId}"，重复插入
    会因主键冲突自然失败，无需额外锁。

D8 软删除与"旧数据必须保留"
  - 删除题目：置 deleted=true，不物理删除。历史答卷仍可解释、
    统计时可单独标注或排除；硬删除会让历史答案变悬空引用。
  - 问卷发布后原则上不改题目语义；确需大改 = 新建题目 + 软删
    旧题，新旧答卷各自完整可解释。
  - 选项 key 不复用（见 D3），同属此类保护。

D9 schema_version 与 settings 扩展位
  - 每个文档带 schemaVersion: 1，第二阶段若做数据迁移，脚本可
    按版本增量迁移，老数据不会被"一刀切"重写。
  - surveys.settings / users.profile 是专门留的扩展容器，新增
    开关类需求先落这里，不动主体字段。

D10 为什么这套设计适合 MongoDB、而不是关系数据库？
  - 题目是"同构公共头 + 异构配置"的数据：关系库要么一张宽表
    放所有校验列（大量空值），要么拆出 option 表 + 多张校验
    明细表 + EAV（查询要五六个 JOIN）；文档模型一个 config
    子文档天然装下。
  - 系统的三个高频读都是"聚合形"的（整卷渲染、整卷提交、按卷
    统计），文档边界与读写边界一致，不需要 JOIN。
  - 两阶段需求变更是明确的：文档模型加字段零迁移成本，正好
    匹配"演化式开发"的作业主题。
  同时承认边界：用户名唯一、外键存在性这类约束 MongoDB 不替你
  保证，由应用层（+ 唯一索引）兜底；对课程系统这是合理取舍。

四、索引设计
----------------------------------------------------------------
users:        { username: 1 }  unique
surveys:      { slug: 1 }  unique                              // 链接访问
surveys:      { ownerId: 1, status: 1, createdAt: -1 }         // 我的问卷列表
questions:    { surveyId: 1, order: 1 }                        // 整卷渲染
responses:    { surveyId: 1, submittedAt: -1 }                 // 统计/翻页
responses:    { surveyId: 1, "respondent.userId": 1 }          // 防重复提交查询
（启用 survey_stats 时：{ surveyId: 1 } unique）

五、功能 → 数据访问映射（核对需求覆盖）
----------------------------------------------------------------
注册/登录               users 插入 / 按 username 查询
创建问卷                surveys 插入（slug 生成）
发布/关闭/截止          更新 surveys.status / 读时比对 deadline
添加题目                questions 插入（order 递增）
分享链接 /survey/slug   surveys 按 slug 查 + questions 按 surveyId 查
填写校验                逐题用 type→校验器解释 config（七）
跳转                    逐题解释 jumpRules（2.3.3）
提交                    responses 插入（多选/单选 value 形态见 2.4）
匿名/多次填写           surveys.allowAnonymous / allowMultipleSubmissions
单题与整卷统计          聚合管道（六）

六、统计实现方案
----------------------------------------------------------------
思路：聚合管道出"裸数字"，应用层合并题目定义出"带标签的结果"。
两步走，避免 $lookup 也能拼出可读报表：

第一步（管道，以单卷为例）：
  $match: { surveyId }            // 命中 responses 索引
  $unwind: "$answers"             // 摊开到每题每答
  $group: {
    _id: { qid: "$answers.questionId", val: "$answers.value" },
    count: { $sum: 1 }
  }
  多选题 value 是数组，统计前对该类答案再 $unwind 一次（按题型
  分流，或统一对 value 做 $unwind——单值为标量不受影响）。

第二步（应用层）：
  查出该卷全部 questions（含软删的，用于标注），按 _id 建字典，
  把 {qid, val} 翻译成"第 3 题：男 = 12 票 / 女 = 20 票"。
  数字填空的平均值：$group 时对 number 类答案同场计算
  { $avg / $min / $max: "$answers.value" }；
  文本填空：直接列出该题全部 value。

某一道题的统计 = 同一管道最前面加 $match answers.questionId。
交叉/按时间过滤等第二阶段可能的新统计维度，都只是给这条管道
加阶段，不动存储。

七、代码侧配套：让"逻辑不写死"真正落地
----------------------------------------------------------------
数据库只完成一半，另一半是解释器的组织方式（以 Node/Python 为例）：
  QUESTION_TYPES = {
    "single_choice": SingleChoice,   // 各自实现：
    "multi_choice":  MultiChoice,    //   validate(config, value) -> errors
    "text":          TextBlank,      //   normalize(raw) -> value
    "number":        NumberBlank,    //   aggregateStage()（供统计）
  }
  - 填写校验 = 查表调用 validate()；跳转 = 独立的 jumpEvaluator(
    question, value) 函数，按 2.3.3 语义解释 jumpRules。
  - 新增题型 = 注册一个新类，数据库零改动；
  - 可以再加一层保险：对 questions 建 MongoDB $jsonSchema 校验，
    保证 type/options 等关键字段入库即合法。

八、第二阶段演进预案（需求来了怎么改）
----------------------------------------------------------------
新题型              新 type 字符串值 + 新校验类；旧题旧答卷不动
新校验限制          config 加字段，解释器缺省视为"不限制"，
                    旧文档缺字段依然合法
新跳转条件/组合条件 match 支持 conditions 数组 + combine(and/or)，
                    单条件视为一元组合，向后兼容
新问卷级开关        落 surveys.settings，不动主体字段
新统计口径          聚合管道加阶段（按时间、按人群、交叉表），
                    存储层无感
数据组织方式变化    保留原集合，写带版本号的迁移脚本增量搬迁，
                    依据 schemaVersion 分批处理；不做"推倒重做"
功能下线            用标记位停用（如 status/deleted），不删数据

九、明确要避免的反模式（对照作业要求自查）
----------------------------------------------------------------
[ x ] 所有数据塞一个集合                  —— 违反"勿存一个集合"
[ x ] 答卷嵌入问卷文档                    —— 无界数组/16MB/并发热点
[ x ] 答案或跳转规则存选项文本            —— 文案一改全错
[ x ] 跳转/校验写死在代码 if-else         —— 违反"勿把逻辑写死"
[ x ] 每次提交 $inc 问卷答卷数又不对账     —— 无收益的冗余
[ x ] 硬删除已有答卷的题目                —— 历史数据变悬空引用
[ x ] 为"看起来规范"给每处都做冗余        —— 违反"谨慎使用冗余"

十、一句话总结
----------------------------------------------------------------
用"4+1 集合 + 判别联合题型 + 数据化校验/跳转 + 软删除保历史"
四件套，把所有会变的东西都变成数据、把所有不变的东西都变成
索引和唯一约束 —— 这就是本设计可扩展、可维护的原因，也是它
比关系型方案更适合本项目的原因。

================================================================
第二阶段：题目资产化（身份 + 版本链 + 共享 + 跨问卷统计）
================================================================

〇、需求变更带来的本质变化
----------------------------------------------------------------
第一阶段的前提是「题目 = 问卷私有的内容」（questions 自带 surveyId）。
八条新需求（保存复用 / 共享 / 已发布不可改 / 修改历史 / 多版本并存 /
使用反查 / 题库 / 跨问卷统计）共同否定这个前提：题目在用户心里是
独立资产，问卷只是"使用"题目。因此第二阶段把题目拆成三个正交概念：

  身份（rootId）    —— 这道题是"哪一道"，跨问卷跨版本不变
  版本（versions）  —— 内容快照 v1 → v2 → v3，只增不改写
  实例（questions） —— 某问卷使用某内容快照的落地文档（第一阶段形态保留）

一、总体架构：5 个集合
----------------------------------------------------------------
users / surveys / responses      完全不变（旧数据零迁移）
questions                        演化：保持"问卷内题目实例"，新增血统字段
question_bank（新）              题目资产：身份 + 内嵌版本链 + 共享名单

questions 实例文档（v2，在 v1 形状上加字段）：
{
  "_id": ObjectId,              // 问卷内题目的对外 id（编辑/答题/答卷存储都用它）
  "surveyId": ObjectId,
  "rootId": ObjectId,           // → question_bank._id（题目身份）
  "bankVersion": 1,             // 内容源自题库第几版（本地编辑=该版的本地快照）
  "basedOn": ObjectId | null,   // 本卷内被替换的前一实例（copy-on-write 分叉）
  "order": 3,
  "type": ..., "title": ..., "required": ..., "options": [...], "config": {...},
  "jumpRules": [...],           // 跳转属于问卷编排，留在实例上
  "deleted": false,
  "schemaVersion": 2,
  "createdAt", "updatedAt"
}

question_bank 身份文档：
{
  "_id": ObjectId,              // 即 rootId
  "ownerId": ObjectId,          // 身份归属（v1 迁移题 = 问卷创建者）
  "sharedWith": [ObjectId],     // 共享给哪些用户（需求二）
  "versions": [                 // 内嵌版本链（需求四、五）
    { "version": 1, "basedOn": null, "editorId": ..., "createdAt": ...,
      "content": { type, title, required, options, config } }
  ],
  "currentVersion": 1,
  "deleted": false,             // 身份级软删（从题库移除，问卷实例不受影响）
  "createdAt", "updatedAt"
}

为什么版本链内嵌在身份文档里？——"题库详情页/版本历史页"的一次读取
单位就是"这道题的全部版本"，内嵌一次查齐；版本由人工编辑产生，
数量天然有界，与"答卷不可嵌入问卷"的无界数组有本质区别
（这是总原则 2 和原则 5 的又一次应用，而非违反）。

二、为什么选"实例持有内容快照"而不是"引用集合"
----------------------------------------------------------------
曾考虑过经典的引用模型（新建 survey_questions 引用集合指向全局版本文档），
最终放弃，原因有三：
1. 第一阶段全部对外语义都围绕"题目实例 id"流转（编辑/删除/排序/答题键/
   答卷存储/统计过滤）。实例持有快照使这些接口的形态与语义全部保持不变，
   71 个第一阶段测试无需改动即通过——"不得推倒重做"的最有力证据；
2. responses.answers.questionId 指向实例 id，而实例内容一经收集即冻结
   （见 D12），"答案永远指向答题时的内容"天然成立，不需要任何补偿逻辑；
3. 题库身份被删（从题库移除）时，问卷实例因持有快照而完全不受影响——
   资产生命周期与问卷生命周期解耦得更彻底。
代价：同一版本内容加入多份问卷会存多份快照（克制的冗余），换来的是
读取路径全部单集合化。课程规模下这是明确划算的取舍。

三、关键设计决策（第二阶段）
----------------------------------------------------------------
D11 身份与版本分离（rootId / versions）
  需求四（历史溯源）、五（多版本并存）、八（跨问卷统计"同一道题"）
  都需要一个跨问卷、跨版本不变的标识。rootId 是身份，版本文档是内容；
  "恢复旧版本"= 以旧内容追加新版本，历史永不改写。

D12 改题规则：copy-on-write（需求三的直接落地，第一阶段唯一行为修正）
  判据 frozen(survey) = status != "draft" 或已有答卷：
  - 未冻结（草稿无答卷）→ 实例原地更新（第一阶段行为）；
  - 已冻结 → 生成分叉：新实例（新 _id、basedOn=旧、接管 order），
    旧实例软删退役，同卷其他题目的跳转目标自动改指新实例。
  旧答卷仍指向旧实例（内容未动），统计按 rootId 归并（见 D14）。
  第一阶段"暂停后原地改题"的路径被此规则取代——这正是用户投诉的场景。

D13 资产生命周期与问卷解耦（第二阶段中期需求调整）
  初版口径是"问卷内建题自动为创建者建立身份 v1（题库随使用自动积累）"，
  试用后调整为**显式入库**：建题默认卷内私有（rootId 为空），用户点
  「存入题库」才创建身份（实例内容即 v1）。理由：自动入库让题库被草稿期的
  过程题填满，违背"题库 = 精选可复用资产"的心智；显式入库让题库语义干净。
  技术含义：未入库题目没有身份，卷内统计的归并键从 rootId 退化为
  "basedOn 血统链的根实例"（分叉仍归并为一行）；已入库题目不受影响。
  其余口径不变：问卷删除级联删除实例与答卷但身份保留；身份从题库移除
  （软删）不影响任何问卷实例。

D14 统计按 rootId 归并
  同一身份在同一问卷内至多一个活跃实例（应用层约束，重复入卷返回 409），
  因此卷内统计可安全地按 rootId 分组：行 id = 锚点实例（该身份在本卷的
  最早实例，历史答卷即存此 id），展示内容 = 最新活跃实例，计数 = 全部
  实例合计——分叉前后"同一道题"的答卷合并展示，被删选项归入
  "（已删除的选项）"行。跨问卷统计同理：先按身份收集全部实例 id，
  再走同一套聚合管道（$match answers.questionId ∈ 实例集）。

D15 跳转规则留在实例上（不进题库）
  goto 指向"本卷内的实例 id"，跳转是问卷语境的编排逻辑，不是题目资产；
  题库题不带跳转，入卷后从空配置开始。好处：同一身份被多卷使用时
  跳转互不串扰；分叉时 goto 重映射只发生在本卷内。

D16 共享是最小权限的名单制
  sharedWith 数组 + 所有者写/被共享者读：被共享者可查看版本、选题入卷、
  看使用与统计；改版本、再共享、存回题库仅所有者。不引入"公开题库"
  这类更大暴露面（需求只要求共享给指定用户）。

四、v1 → v2 数据迁移（scripts/migrate_v1_to_v2.py）
----------------------------------------------------------------
对每个无 rootId 的存量题目：创建身份（owner = 问卷创建者，v1 内容即
版本链第 1 版），题目文档补 rootId/bankVersion=1/basedOn=null。
- responses 一行不动：answers.questionId 存的实例 id 迁移前后不变；
- surveys / users 不动；jumpRules 不动（goto 指向的实例 id 不变）；
- 幂等可重跑，已迁移题目自动跳过；
- 迁移后老用户的历史题目自动出现在其题库中（需求一的惊喜副作用）。

五、索引（第二阶段新增）
----------------------------------------------------------------
questions:      { rootId: 1 }                        // 使用反查/跨卷统计
question_bank:  { ownerId: 1, deleted: 1 }           // 我的题库
question_bank:  { sharedWith: 1 }                    // 共享给我的

六、八条需求 → 数据结构映射（自查）
----------------------------------------------------------------
一 保存复用       身份独立于问卷；from-bank 选题入卷（可多卷）
二 共享           sharedWith 名单；共享双方用同一 rootId
三 已发布不可改   frozen 判据 + copy-on-write 分叉；旧实例软删保留
四 修改历史       versions 内嵌版本链（basedOn 溯源）；恢复=追加新版
五 多版本并存     各卷实例钉不同 bankVersion；升级按 frozen 选原地/分叉
六 使用反查       questions 按 rootId 查实例 → 按问卷归并
七 题库管理       question_bank 的 CRUD + 版本追加 + 升级换绑
八 跨问卷统计     实例 id 集 → 同一套聚合管道 → 按 rootId 归并 + 分卷明细
